### 3.1 Componentes de seleção assíncrona (`@shared/components/selectors/`)

Padrão para inputs de busca (`ng-select2-component`) que buscam no backend conforme o usuário digita — introduzido em `company-selector`:

- `<select2 [customSearchEnabled]="true" ...>` com `(search)` emitindo pro componente, que empurra o termo digitado num `Subject` interno e usa `switchMap` pro `<entidade>Service.byLike(q)` (cancela automaticamente a busca anterior se o usuário continuar digitando).
- Carga inicial (sem termo) já dispara `byLike('')`, trazendo os N primeiros registros do backend — não fica esperando o primeiro caractere.
- Pré-seleção pra telas de edição: método público `autoset(id)` (chamado via `@ViewChild` pelo componente pai) que busca o registro por id (`service.get(id)`) e garante que ele apareça no `data`/`value` do `<select2>` mesmo que não esteja entre os N primeiros trazidos pelo `byLike`.
- Seleção do usuário é emitida via `@Output() selected` com a entidade completa (não só o id) — quem usa o componente decide o que fazer (setar num `FormControl`, etc.).
- **Não implementa `ControlValueAccessor`** (sem precedente disso no projeto ainda) — não dá pra usar `formControlName` direto no `<app-company-selector>`, só `@Output()`/método público. Se surgir a necessidade de um form usar `formControlName` diretamente no seletor, avaliar introduzir CVA nesse momento (o próprio `<select2>` já suporta, via auto-registro em `NgControl` — ver `ng-select2-component`).
- `Select2` não expõe `valueChange`, então `[(value)]` (banana-in-a-box) não funciona sem `ngModel`/`formControl`; usar `[value]` (one-way) e atualizar a propriedade do componente host imperativamente — o setter interno do `<select2>` já resincroniza a UI.
- Markup: `<select2>` + botão "Limpar" (ícone `fa-solid fa-eraser`) dentro de um `.input-group` do Bootstrap. Como `<select2>` é um elemento custom (não `.form-control`/`.form-select`), o CSS nativo do `.input-group` não estica ele sozinho — precisa de `select2 { flex: 1 1 auto; min-width: 0; }` no `.scss` do próprio componente (ver `company-selector.component.scss`).
- **Seletores dependentes de outra seleção** (`customer-selector`, `employee-selector` dependem de `companyId`): expõem `@Input() companyId`, desabilitam o `<select2>` (`[disabled]="!companyId"`) enquanto não houver company, e usam `ngOnChanges` pra resetar seleção/lista e refazer o `byLike('')` quando o `companyId` muda. O `autoset(id)` continua independente de `companyId` (busca direta por id via `service.get(id)`).
- **Busca por múltiplos campos** (`user-selector`, busca por `name` OU `email`): o backend usa `where` como array de condições (`[{ name: Like(...) }, { email: Like(...) }]` — array = OR no TypeORM), não um objeto único.
- **Cuidado com over-fetch de campos sensíveis no `byLike`**: o `find()` do TypeORM sem `select` explícito devolve a entidade inteira — no `UsersService.byLike` isso vazava o hash da senha (`password`) pra qualquer usuário autenticado que buscasse no seletor. Corrigido com `select: ["id", "name", "email"]`. Ao criar um novo `byLike`, checar se a entidade tem colunas sensíveis (senha, tokens, documentos não necessários pro label) antes de devolver a lista inteira.
- **Filtro por relação many-to-many no `byLike`** (`user-selector`, restringe por `roleTypes: RoleEnum[]` e/ou `roleIds: string[]`): como `UserEntity.roles` é `ManyToMany`, `repository.find()` simples não dá conta de filtrar por role sem duplicar linhas — trocado por `QueryBuilder` com `innerJoin("user.roles", "role") + .distinct(true)` (o `distinct` evita usuário duplicado quando ele bate em mais de uma role do filtro). Params de array em query string GET (`roleTypes`, `roleIds`) chegam como string quando só há um valor e como array quando há vários — o DTO usa um `@Transform` (`toArray` em `find-by-like-user.dto.ts`) pra normalizar os dois casos antes da validação. No `UserService.byLike` (front), arrays são serializados via `HttpParams.append` (uma entrada por valor), não `.set()` (que sobrescreveria).
- **Cadeia de seletores geográficos** (`country-selector` → `state-selector` → `city-selector`): `country-selector` é independente (mesmo padrão do `company-selector`). `state-selector` depende de `countryId` e `city-selector` depende de `stateId`, seguindo exatamente o padrão de dependência única já documentado acima (`companyId` em `customer-selector`/`employee-selector`).
- **Seletor com múltiplos inputs opcionais, "habilita se pelo menos um" em vez de "habilita se todos"** (`address-selector`, depende de `cityId`, `customerId` e `employeeId`): diferente do padrão de dependência única acima, aqui os três `@Input()` são opcionais e o `<select2>` habilita com base num getter `hasOwner` (`!!customerId || !!employeeId`) — reflete a regra de negócio do backend (`AddressService.getOwnerFilter`, back) de que um endereço pertence a um `customer` OU a um `employee`, nunca aos dois. `cityId` é só um filtro adicional que estreita a busca (não é obrigatório pra habilitar o campo). `ngOnChanges` usa `['cityId','customerId','employeeId'].some(...)` pra detectar mudança em qualquer um dos três e refazer o `byLike('')`. O label da option é montado no componente (`street, number - neighborhood`), já que `Address` não tem um campo `name` único.
- **Novos endpoints REST `by-like`** (`country`, `state`, `city`, `address`, backend): seguem o mesmo padrão dos demais (`Like` do TypeORM, `order by name/street ASC`, rota `GET .../by-like` registrada antes de `:id` no controller). Nenhuma dessas entidades tem coluna sensível, então o `repository.find()` sem `select` explícito é seguro aqui (diferente do caso do `user-selector`, seção acima).

### 3.2 Listas de sub-formulário editável (`@shared/components/form-lists/`)

Padrão para um componente que recebe uma lista de entidades filhas (ex. endereços de um `customer`/`employee`) e gerencia adicionar/editar/remover localmente, devolvendo a lista pronta pra tela-mãe incluir no payload principal — introduzido em `address-form-list`:

- Contrato: `@Input() data: Entity[]` + `@Output() dataChange = new EventEmitter<Entity[]>()`, seguindo a convenção do Angular para permitir `[(data)]="algumaLista"` na tela-mãe. O componente **não persiste nada sozinho** (sem chamada a service/API) — só mantém a lista em memória e a entrega via `dataChange` a cada add/edit/remove; quem usa decide quando/como salvar (ex. embutida no `toModel()` da entidade pai, como já acontece em `CustomerModel`/`EmployeeModel`).
- `dataChange.emit([...this.data])` sempre com um **novo array** (nunca a mesma referência mutada) — evita depender de mutação por referência ficar "visível" pra tela-mãe caso ela vire `OnPush`/signals no futuro.
- Entidades novas são criadas com `new Entity({...})` (constructor), **não** com o `Entity.toEntity(jsonProps)` estático — `toEntity` de várias entidades desse projeto força `created_at: new Date(props.created_at)` mesmo quando `props.created_at` é `undefined`, gerando uma `Invalid Date` que quebra depois em `EntityBase.toModel()` (`.toISOString()` de uma `Invalid Date` lança `RangeError`). O constructor da entidade já tem o fallback certo (`props.created_at ? new Date(...) : new Date()`), então construir direto com `new Entity(...)` evita o bug sem precisar tocar no model compartilhado. Ao editar (`save()`), o novo objeto é montado a partir do original (`{ ...original, ...formValue }`) pra preservar `created_at` e não recriar a entidade do zero.
  - **Causa raiz identificada em 2026-07-20**: o backend serializa as colunas de data como `createdAt`/`updatedAt`/`deletedAt` (nome da propriedade TS em `BaseEntity`, back), não `created_at` como o front espera — então **qualquer** entidade que chegue via HTTP (não só entidades novas montadas na mão) tem `props.created_at === undefined`, e o `toEntity()` de `CountryModel`/`StateModel`/`CityModel`/`AddressModel`/`UserModel`/`RoleModel`/`CompanyModel`/`CustomerModel`/`EmployeeModel` sofre desse bug. Isso não é exclusivo de entidade "nova": os seletores em `@shared/components/selectors/` (`country-selector`, `state-selector`, `city-selector`) também usam `Entity.toEntity(...)` internamente (`byLike`/`autoset`), então **toda** seleção de país/estado/cidade feita por um usuário (não só telas de edição) já vinha com `created_at` inválido.
  - Ao tornar a seleção de país **obrigatória** antes de liberar o resto do formulário (ver bullet abaixo), esse bug deixou de ser um caso raro e passou a estourar em **todo** `add()`/`save()` (a tela-mãe chama `address.toModel()` em `dataChange`, que cascade em `countryEntity.toModel()`/`stateEntity.toModel()`/`cityEntity.toModel()`) — por isso `CountryModel.Entity.toEntity`/`StateModel.Entity.toEntity`/`CityModel.Entity.toEntity` foram corrigidos (mesmo guard que `updated_at`/`deleted_at` já usavam: `props.created_at ? new Date(props.created_at) : new Date()`). `AddressModel` e os demais models (`UserModel`, `RoleModel`, `CompanyModel`, `CustomerModel`, `EmployeeModel`) **continuam com o bug** — não foram tocados porque nenhum fluxo hoje força passar por eles via `toEntity()` (ver débito técnico, seção 7).
- **Pré-seleção de seletores geográficos encadeados (`country` → `state` → `city`) num formulário de edição**: os seletores em `@shared/components/selectors/` não têm `ControlValueAccessor` (seção 3.1) e resetam a si mesmos (`ngOnChanges` → `value = null` + `selected.emit(null)`) toda vez que o `@Input` do nível pai muda (ex. `[countryId]`) depois da primeira vez. Isso significa que, ao chamar os três `autoset(id)` em sequência dentro do mesmo ciclo síncrono, o reset automático do nível de baixo (disparado pela mudança do `[countryId]`/`[stateId]`) pode rodar **depois** do `autoset()` explícito daquele nível e sobrescrever o valor certo com `null`. A solução usada em `address-form-list.component.ts` (método privado `autoset`): setar e chamar `.autoset()` **um nível de cada vez**, sempre em ordem país → estado → cidade, com um `this.cdr.detectChanges()` (via `ChangeDetectorRef` injetado) entre cada nível — isso força o reset do filho a acontecer *antes* de setarmos o próximo nível, então não há nada pra sobrescrever. Não existe (ainda) um caso de edição com seletores encadeados fora desse componente; se aparecer outro, reaproveitar essa técnica em vez de reinventar.
- **Regra "um único endereço principal" (`is_main`) replicada no client**: o backend (`AddressService`, back) garante via transação que só existe um `is_main: true` por `customer`/`employee` (primeiro endereço criado vira principal automaticamente; marcar um novo como principal despromove os outros; remover o principal promove outro). Como esse componente edita a lista **em memória, antes de qualquer POST/PUT**, a mesma regra foi replicada no `add()`/`save()`/`remove()` do componente (métodos privados `demoteOtherAddresses`/`promoteAnotherAddress`) pra lista entregue via `dataChange` nunca ficar com zero ou mais de um endereço principal.
- **País obrigatório primeiro, resto do formulário bloqueado até a seleção** (decisão de produto, 2026-07-20): o seletor de país é o único campo sempre habilitado; os demais (`street`, `number`, `neighborhood`, `complement`, `zip_code`, `type`, `is_main`) começam desabilitados via `FormControl.disable()`/`.enable()` (método privado `setFieldsBlockedUntilCountry`, chamado em `default()`, `onCountrySelected()` e no `autoset()` de edição) — **não** via atributo `[disabled]` no template, porque misturar atributo nativo com `formControlName` gera warning/dessincronia no Reactive Forms. Estado/cidade já ficavam de fato bloqueados de graça, porque `state-selector`/`city-selector` (seção 3.1) já desabilitam sozinhos sem `countryId`/`stateId`. **Cuidado ao reusar este padrão**: como controles desabilitados são excluídos da validade agregada do `FormGroup`, `form.invalid` fica `false` mesmo com país não selecionado (os `Validators.required` dos campos bloqueados não contam) — os botões "Adicionar"/"Atualizar" precisam do guard extra `[disabled]="form.invalid || !form.get('country_id').value"`, não só `form.invalid`.
- **Máscara de CEP + busca automática de endereço — só Brasil por enquanto**: `onZipCodeInput($event)` (ligado ao `(input)` nativo do campo, não a `valueChanges` — importante, porque `valueChanges` também dispara em `setValue()` programático durante o `autoset()` de edição, e isso re-disparava a busca e sobrescrevia os dados que o usuário já tinha editado) só formata/busca quando `countryEntity?.code === 'BR'` (getter `isBrazilSelected`). Formata pra `00000-000` (método privado `formatBrazilianZipCode`, regex simples, sem lib de máscara — projeto não tem `ngx-mask` nem similar instalado) e, ao completar 8 dígitos, chama `AddressService.lookupZipCode(cep)` (novo endpoint `GET /v1/addresses/lookup-zip-code/:zip_code`, back), que devolve `street`/`neighborhood`/`complement` + `country`/`state`/`city` já resolvidos nas tabelas locais. O preenchimento de estado/cidade reusa a técnica de encadeamento com `detectChanges()` entre níveis (mesmo motivo do bullet de pré-seleção acima) — só que aqui começando em `state` (não em `country`, que já foi escolhido manualmente pelo usuário antes do campo de CEP ser liberado). Erro (CEP não encontrado / formato inválido / falha de rede) é mostrado com `AlertService.alert(...)` (ícone `warning`, timer, sem botão de confirmação) — não há um serviço de toast "leve" hoje no projeto (`ngx-toastr` está no `package.json` mas não tem um wrapper usado ativamente em nenhuma tela), então reaproveitou-se o `Swal` do `AlertService`. **Fora de escopo por enquanto** (decisão explícita do usuário): máscara/busca para outros países — o campo fica sem máscara e sem autocomplete pra qualquer país diferente de `BR`.
- **Endpoint `GET /v1/addresses/lookup-zip-code/:zip_code` (backend, novo)**: consulta a API pública da ViaCEP (`https://viacep.com.br/ws/{cep}/json/`, sem autenticação/chave) via `fetch` global do Node (disponível nativamente a partir do Node 18, sem precisar adicionar `axios`/`@nestjs/axios` como dependência nova — é a primeira integração HTTP com serviço externo do backend, ver `AddressService.lookupZipCode`). Resolve `state`/`city` locais casando `uf`/`localidade` da resposta da ViaCEP com as tabelas `states`/`cities` já seedadas (`CountryService.findByCode`/`StateService.findByCode`/`CityService.findByName`, novos métodos) — **depende dos nomes de cidade da ViaCEP baterem exatamente** com o `name` seedado em `cities` (sem fuzzy match, sem normalização de acento/caixa); se não bater, a resposta volta só com `street`/`neighborhood`/`complement` preenchidos e `state`/`city` nulos (o front não quebra, só não encadeia o autoset). Endpoint protegido por `AuthGuard`, mesmo padrão dos demais endpoints do `AddressController`.

### 3.3 Tela de CRUD administrativo completa — lista + filtro + modal (introduzido em `features/admin/parishioners`, 2026-07-20; replicado em `features/admin/employees`, 2026-07-21)

Primeira tela do projeto a sair do estado de "esqueleto" (tabela com dado mockado de `@shared/data/bootstrap-table`, formulário vazio) para uma tela realmente funcional ponta a ponta. `features/admin/employees` (Funcionários) foi criada do zero (não existia pasta/esqueleto ainda) replicando exatamente esses padrões — nenhum padrão novo foi introduzido, só as diferenças de campo já esperadas (`Employee` tem `email` obrigatório na própria entidade, não tem `document`; sincronização de endereços usa `employee_id` em vez de `customer_id`). `features/admin/addresses` (e qualquer outra criada a partir do mesmo gerador/scaffold) **ainda está no estado de esqueleto** — ao finalizá-la, replicar os padrões abaixo em vez de reinventar, e prestar atenção nas armadilhas já mapeadas aqui (a maioria só aparece em runtime, não em `ng build`).

- **Listagem via GraphQL, não REST**: `CustomerService.list(filter, skip, take)` (`@core/modules/general/services/customer.service.ts`) usa `Apollo.query()` contra a query `customerList` (nova, backend, mesmo padrão de `employeeList`/`countryList`/`stateList`/`cityList` já existentes — ver `AI_CONTEXT.md` do backend, seção 3). Motivo de usar GraphQL aqui (diferente do `by-like` dos seletores, que é REST por decisão explícita anterior — seção 7): a tela precisa de paginação real (`meta.totalItems`/`totalPages`) e filtro combinando `like`/`eq` em vários campos, que é exatamente o que `BaseListArgs`/`FilterParam` (backend) já resolvem de forma genérica — reimplementar isso como endpoint REST dedicado duplicaria essa lógica.
  - Filtro do front (`CustomerModel.Filter`) é convertido para `FilterParam[]` em `CustomerService['buildFilterParams']`: `type: 'like'` para `name`/`document` (front já embrulha o valor em `%...%` — o backend não adiciona wildcard sozinho) e `type: 'eq'` para `company_id`/`user_id`. **Todo filtro usa `alias: 'c'`** (alias da tabela principal na query, definido no backend em `GeneralGraphqlService.customerList`) — sem isso, filtrar por `name` dá erro de coluna ambígua, já que a query faz `innerJoin` com `company`, que também tem coluna `name`.
  - **Pré-requisito que não existia**: o endpoint Apollo em `app.config.ts` era um placeholder de template nunca preenchido (`uri: '<%= endpoint %>'`) — o GraphQL client nunca funcionou antes desta tela. Corrigido para `` `${environment.api.url}/graphql` ``. Se uma tela GraphQL não funcionar e o erro for de rede/URL inválida, checar isso primeiro.
- **Sincronização de endereços é client-orchestrated, não aninhada no payload do customer** (`FormComponent.submit()`/`syncAddresses`, `parishioners/_components/form/form.component.ts`): `CreateCustomerDto`/`UpdateCustomerDto` (backend) não aceitam um campo `addresses[]` — só os campos escalares do próprio customer. O componente salva o customer primeiro (sem `addresses` no body — removido explicitamente antes do `create`/`update`), depois compara a lista atual (`form.get('addresses').value`) com `originalAddressIds` (ids carregados no `load()`) e dispara `AddressService.create`/`.update`/`.delete` (um request por endereço, via `forkJoin`) só depois que o id do customer é conhecido. **Cada endereço precisa ser reduzido a um payload limpo** (`street, number, complement, neighborhood, zip_code, type, is_main, country_id, state_id, city_id, customer_id`) — mandar o objeto como `AddressModel.Entity.toModel()` devolve (`id`, `created_at`, `country`/`state`/`city` aninhados etc.) direto pro `AddressService.create/update` quebra com `403`/`400` (`whitelist`/`forbidNonWhitelisted` do backend rejeita campo que `CreateAddressDto`/`UpdateAddressDto` não declaram). Ver débito na seção 7 (não é atômico entre customer e endereços).
- **`ngbNav` recria o conteúdo da aba inativa por padrão (`destroyOnHide`)** — qualquer sub-form de aba (`BasicFormParishionerComponent`, `AddressesComponent`) que dependa de estado carregado antes da aba existir (ex. pré-seleção de `company-selector`, lista de endereços) precisa **se auto-inicializar a partir do form pai** (fonte da verdade, sobrevive à troca de aba) no próprio `ngOnInit`/`ngAfterViewInit`, e não só confiar numa chamada explícita do componente pai feita uma única vez (ex. logo após o `load()` da tela de edição) — essa chamada só alcança a aba que estiver ativa **naquele exato instante**; abas ainda não visitadas (ou revisitadas depois de trocar e voltar) perdem o estado se não se auto-inicializarem.
  - **Cuidado com `@ViewChild` em `ngOnInit`**: não está resolvido ainda nesse hook (só a partir de `ngAfterViewInit`). Auto-inicialização que dependa de `@ViewChild` (`BasicFormParishionerComponent.autoset()`, que chama `companySelectorRef.autoset(id)`) precisa rodar em `ngAfterViewInit`, não em `ngOnInit` — colocar em `ngOnInit` faz o `@ViewChild` estar `undefined` silenciosamente (sem erro) e a pré-seleção simplesmente não acontece na primeira vez que a aba é destruída/recriada. `AddressesComponent.autoset()` não depende de `@ViewChild` (só lê `form.get('addresses').value` pra um array local), então essa auto-inicialização já podia ficar em `ngOnInit` sem problema.
- **`FilterStore` precisa ser provido num ancestral comum, não dentro do próprio `FilterComponent`**: o padrão copiado de tela em tela (`providers: [FilterStore]` no `@Component` do `FilterComponent`) só funciona enquanto ninguém fora do `FilterComponent` (ou de um descendente dele) tenta injetar o mesmo `FilterStore` — a injeção de dependência do Angular resolve um provider local para o próprio componente e seus **descendentes**, nunca para um ancestral. Assim que `DataListComponent` (pai de `FilterComponent` no template) passou a injetar `FilterStore` no construtor pra escutar mudança de filtro e disparar a busca, a tela quebrou em runtime com `NG0201: No provider found for FilterStore` (não aparece em `ng build`/`tsc`, só ao navegar pra tela). Corrigido movendo `providers: [FilterStore]` para `DataListComponent` (ancestral comum de `FilterComponent` e de si mesmo) e removendo do `FilterComponent`. **`features/admin/addresses` tem exatamente o mesmo `providers: [FilterStore]` isolado no `FilterComponent` e ainda não foi corrigido** — só não quebrou porque o `DataListComponent` de lá ainda não injeta `FilterStore` (continua com dado mockado). Vai quebrar do mesmo jeito assim que essa tela for finalizada; aplicar a mesma correção nesse momento.
- **`CustomerService.get()`/`EmployeeService.get()` (backend) precisaram ganhar `relations: [...]`** — `BaseCrudService.get()` usa `findOneBy` puro, que nunca carrega relations. Sem esse override, a tela de edição carregava o registro mas `company`/`user`/`addresses` sempre vinham `undefined`, então a aba de endereços aparecia vazia mesmo com endereços já salvos no banco (só percebido testando manualmente o fluxo de edição ponta a ponta, não em tipo/lint). `EmployeeService.get()` replicou a mesma correção ao finalizar a tela de Funcionários. **Atualização 2026-07-21**: o primeiro `relations: ["company", "user", "addresses"]` não bastava — faltavam as relações aninhadas do endereço (`addresses.country`/`addresses.state`/`addresses.city`), então a tabela de endereços mostrava "-" em Cidade/Estado/País ao editar um registro com endereço salvo (`item.city?.name` etc. vinham `undefined`). ### 3.4 Exportação Excel com escopo "lista completa" vs "lista filtrada" (introduzido em `features/admin/parishioners`, 2026-07-21)

Botão "Exportar Excel" da tela de Paroquianos (`data-list.component.ts`), antes só decorativo, virou um `ngbDropdown` (mesmo módulo `NgbDropdownModule` já usado em `card-dropdown-button`) com duas opções — "Lista completa" (ignora o filtro atual, `new CustomerModel.Filter({})`) e "Lista filtrada atual" (reusa `this.filter`, o mesmo state já sincronizado via `FilterStore`) — nenhuma das duas fica restrita à página atual da tabela (`take: 100000` na query, ver abaixo).

- **Biblioteca: `exceljs`, não `xlsx` (SheetJS)** — a versão do pacote `xlsx` publicada no npm está desatualizada (SheetJS parou de publicar lá, mantém só via `cdn.sheetjs.com`) e carrega duas vulnerabilidades conhecidas (`npm audit`): prototype pollution e ReDoS. Como não teríamos como aplicar o fix oficial via npm registry, trocado por `exceljs` (mantido, sem CVE ativo). `exceljs` tem um `"browser": "./dist/exceljs.min.js"` no `package.json` — o builder do Angular (esbuild) já respeita esse campo sozinho, então funciona direto no bundle do browser sem precisar de polyfill de `fs`/`stream` do Node (confirmado via `ng build`, sem warning de "Could not resolve").
  - `exceljs` ainda carrega uma cópia própria (nested) de `uuid@^8.3.0` com uma vulnerabilidade moderada (`GHSA-w5hq-g745-h8pq`, bounds check em `v3/v5/v6` com `buf` custom — não é um caminho que a lib realmente exercita aqui, mas o `npm audit` acusa mesmo assim). Corrigido com `overrides.exceljs.uuid` no `package.json` (mesmo padrão que os overrides já existentes de `ngx-owl-carousel-o`/`angular-datetime-picker`), forçando a mesma versão (`^14.0.1`) que o projeto já usa como dependência direta.
  - `ExcelExportService` (`@shared/services/excel-export.service.ts`) é o wrapper genérico (`export(filename, sheetName, columns, rows)`): monta o workbook, `workbook.xlsx.writeBuffer()` (retorna `Promise`, por isso o método é `async`) e dispara o download via `Blob` + `<a download>` + `URL.createObjectURL`/`revokeObjectURL` — sem `file-saver` (não precisa: navegador já lida com isso nativamente a partir do buffer).
- **Endereço principal only, sem sobrecarregar a listagem paginada**: como um customer pode ter N endereços mas o Excel só mostra o principal, criada uma query GraphQL separada no front (`CUSTOMER_EXPORT_QUERY`, `customer.service.ts`) — mesma query `customerList` do backend, só que pedindo o campo `addresses` também. A query da tabela paginada (`CUSTOMER_LIST_QUERY`) continua sem esse campo, pra não engordar o payload de toda troca de página/filtro à toa.
  - **Backend (`GeneralGraphqlService.customerList`)**: `addresses` é `OneToMany` (joins diretos duplicariam a linha do customer por endereço — mesmo problema que os comentários de `company`/`user` no código já alertavam pro caso ManyToOne). Resolvido com `leftJoinAndSelect("c.addresses", "address", "address.is_main = :isMain", { isMain: true })` — a condição do join restringe a **no máximo 1** endereço por customer (a regra de negócio já garante endereço principal único por `customer`/`employee`, ver `AddressService`), então não há risco de duplicar linha nem de estourar a paginação. Os relations aninhados (`address.city`/`address.state`/`address.country`) também precisaram de `leftJoinAndSelect` explícito — sem isso viriam `null` mesmo com o schema GraphQL já expondo esses campos (`Address`/`City`/`State`/`Country` já são `@ObjectType()` com `@Field` desde antes, usados aqui pela primeira vez via GraphQL — antes só a REST/`AddressService.get()` exercitava essas relations).
  - Sem endpoint/flag de "export" dedicado no backend — reaproveita o mesmo resolver/método `customerList`, só que chamado com `take: 100000, skip: 1` (sem cap server-side em `BaseListArgs`, confirmado em `base-list-args.dto.ts`) em vez do `take` de 10 da paginação da tela.
- **Débito conhecido**: esse padrão (dropdown de exportação + `is_main`-only join + `ExcelExportService`) só existe em Paroquianos até agora. `features/admin/companies`/`employees` não têm botão de exportação; `features/admin/addresses` tem o botão comentado (`<!-- Exportar Excel -->`, esqueleto). Se/quando outra tela precisar do mesmo recurso, reaproveitar `ExcelExportService` (já genérico) e replicar o join `is_main` no resolver correspondente (`employeeList`, mesmo arquivo) em vez de reinventar.
- **Gotcha de CSS do tema**: `public/assets/scss/components/_dropdown.scss` tem uma regra genérica `.dropdown .dropdown-toggle { width: 100px; }`, pensada pro dropdown compacto do `card-dropdown-button` (labels curtas tipo "Recente"/"Popular"). Qualquer novo `ngbDropdown` com texto mais longo (ex. "Exportar Excel"/"Exportando...") precisa sobrescrever `width: auto` + reservar espaço pra seta (`::after`, `position: absolute; right: 10px`, também do tema) com `padding-right` — senão o texto sobrepõe a seta. Resolvido com uma classe própria (`.export-dropdown`) no `data-list.component.scss` da tela, não editando o scss do tema.
- **Enum devolvido pelo GraphQL vem como o nome da chave, não o valor** (`item.gender` na `CUSTOMER_EXPORT_QUERY`): `registerEnumType(GenderEnum, ...)` (backend) expõe o enum no schema GraphQL usando as chaves (`MASCULINE`/`FEMININE`), não os valores em minúsculo armazenados no banco (`masculine`/`feminine`, os mesmos usados pelo REST/`CreateCustomerDto` e pelo `<select>` do formulário). `downloadExcel` (`data-list.component.ts`) faz `item.gender.toLowerCase()` antes de consultar `GENDER_LABELS` por causa disso — sem o `toLowerCase()`, a coluna "Gênero" do Excel saía com `"MASCULINE"` em vez de `"Masculino"`. Só afeta leitura via GraphQL; o formulário (REST, `CustomerService.get()`) não tem esse problema.

### 3.5 Núcleo familiar (pai/mãe) no formulário de Paroquianos (introduzido 2026-07-21)

Aba "Dados Básicos" (`BasicFormParishionerComponent`) ganhou `gender`, `birthdate`, `place_birth`, `father_id` e `mother_id` — campos escalares simples no `FormGroup` do `FormComponent` (`parishioners/_components/form/form.component.ts`), sem sincronização client-orchestrated como em endereços (seção 3.3): `CreateCustomerDto`/`UpdateCustomerDto` já aceitam esses campos direto no payload do customer.

- **Pai/mãe são o próprio `Customer` (auto-relacionamento), não um `User`** — `CustomerModel.Entity.father`/`.mother` (front) estavam tipados como `UserModel.Entity` (bug pré-existente, provavelmente copiado de `user_id` por engano); corrigido pra `Entity` (self-reference), espelhando `Customer.father`/`.mother` do backend (`ManyToOne(() => Customer)`). `JsonProps` também precisou declarar `father?: JsonProps` / `mother?: JsonProps` (self-referência no próprio type alias — válido em TS) e `toModel()`/`static toEntity()` ganharam os mesmos ramos que já existiam pra `user`/`company`.
- **Reaproveitado o `customer-selector` já existente** (seção 3.1) pros campos "Pai"/"Mãe" — mesma dependência de `companyId` que os outros usos dele (pai/mãe precisam pertencer à mesma paróquia do paroquiano sendo editado). Duas instâncias do componente na mesma tela (uma pra cada campo) foram o que expôs o bug de tipo do `autoset()` documentado na seção 7 (o `ng build`/`ng serve` real só quebrou ao existir >1 instância montada ao mesmo tempo nessa tela).
- **`companyId` sincronizado via propriedade do componente, não lido direto do form no template**: `BasicFormParishionerComponent.companyId` é setado já no `ngOnInit` (antes da view existir, a partir de `form.get('company_id').value`) — necessário pra que os dois `customer-selector` (que dependem de `@Input() companyId`) já nasçam com o valor certo na primeira detecção de mudança, e não fiquem desabilitados até o próximo evento. `onCompanySelected()` atualiza a mesma propriedade quando o usuário troca a paróquia manualmente, e os `customer-selector` de pai/mãe se resetam sozinhos (padrão já documentado na seção 3.1).

- **Sem validação de auto-referência (um paroquiano ser pai/mãe de si mesmo) nem de ciclo** — nem client nem backend impedem isso hoje; o `customer-selector` de pai/mãe lista todos os paroquianos da paróquia, incluindo o próprio registro em edição. Ficou de fora por decisão de escopo (não pedido), não por esquecimento.

- Testado manualmente ponta a ponta em 2026-07-21 (Playwright headless + `ng serve` local + backend Docker): criação com paróquia/gênero/data/local de nascimento/pai/mãe preenchidos, edição reabrindo com os cinco campos corretos, exportação Excel com as cinco colunas novas. Ver seção 7 pro bug de `ng build` encontrado e corrigido durante esse teste.

### 3.6 Módulo financeiro — Serviços Financeiros + Faturas/Pagamentos (introduzido 2026-07-22)

Duas telas novas em `features/admin/financial-services/` (catálogo) e `features/admin/financial-bills/` (Faturas), consumindo `@core/modules/financial/` (entidades/services novos, mesmo padrão namespace-por-arquivo de `CustomerModel`/`AddressModel` — enums do backend replicados **dentro** do namespace do model, ex. `FinancialBillModel.StatusEnum`, não em arquivo `enums/` separado, seguindo a convenção já usada em `AddressModel.AddressTypeEnum`, não a do backend). Escopo decidido com o usuário: CRUD completo de Fatura (não só registro de pagamento avulso), com paróquia sempre credora (arco "paróquia deve ao paroquiano"/estorno fica fora de escopo) e filtro por `company_id` replicado no client (mesmo gap de multitenancy do backend, ver `AI_CONTEXT.md` do backend §"Multitenancy").

- **`financial-services`**: CRUD simples (name, description, price, active, company), sem abas múltiplas (só "Dados Básicos", 1 aba, mesmo padrão de `companies`) — pré-requisito pro catálogo usado nos Itens de Fatura e no futuro fluxo de contratação de batismo (que vai referenciar um `FinancialService` "Taxa de Batismo" já cadastrado aqui).
- **`financial-service-selector`** (`@shared/components/selectors/`): diferente dos demais seletores (seção 3.1), **não usa `customSearchEnabled`/`(search)` remoto** — o endpoint `GET /v1/financial-services/by-company/:company_id` já devolve a lista inteira de ativos da paróquia de uma vez (sem paginação/termo), então o filtro é feito localmente pelo próprio `<select2>`. `autoset(id)` cai pro `FinancialServiceService.get(id)` se o serviço não estiver na lista de ativos carregada (ex.: item de fatura antigo referenciando um serviço já desativado).
- **`financial-bills`**: fatura tem 3 abas — "Dados Gerais" (paróquia + devedor via `company-selector`/`customer-selector`, `release_date`, `total`, `status`), "Itens" (opcional) e "Parcelas / Pagamentos".
  - **Seletores de paróquia/devedor ganharam `@Input() disabled`** (`CompanySelectorComponent`/`CustomerSelectorComponent`, `@shared/components/selectors/`) — novidade desta tela: em modo edição, trocar quem deve numa fatura já emitida é considerado fora de escopo (mudaria o ator financeiro por trás), então os seletores ficam desabilitados (mas visíveis, mostrando o nome via `autoset`) via esse novo input opcional (default `false`, não quebra os demais usos existentes).
  - **Dual-mode nas abas "Itens" e "Parcelas" (`items.component.ts`/`installments.component.ts`)** — padrão novo, não generalizado em `@shared/form-lists` porque (ainda) só existe esse caso de uso: sem `billId` (fatura em criação), a lista vive em memória e é sincronizada no controle `items`/`installments` do form pai (`@Input() billId: string | null`, lidos via `ControlContainer`, mesmo mecanismo de `AddressesComponent`), embarcada inteira no `POST /v1/financial-bills` (`CreateFinancialBillDto.installments`/`.items`, backend exige ao menos 1 parcela — validado no client antes do submit, mesma mensagem de erro). Com `billId` (fatura já existe, modo edição), cada ação (adicionar/remover item, adicionar parcela) chama o service correspondente (`FinancialBillItemService`/`FinancialInstallmentService`) **imediatamente**, sem esperar um "Salvar" geral — diferente do padrão de Address (seção 3.2), que sempre sincroniza no submit do pai. Motivo: parcelas/pagamentos de uma fatura já emitida fazem sentido como ações imediatas (é literalmente a tela de "gerenciamento de pagamento"), não como rascunho a ser descartável.
    - Editar um item já existente (mudar `quantity`/`unit_price` de uma linha) **não é suportado** — só adicionar/remover. Decisão de escopo (não de limitação técnica; o backend expõe `PUT /v1/financial-bill-items/:id`), pra não multiplicar formulários; remover + adicionar de novo cobre o caso.
  - **Registro de pagamento e recálculo client-orchestrated de `paid_out`/status da fatura** (`InstallmentsComponent.registerPayment`) — o backend **não** tem regra de negócio nenhuma em `FinancialTransactionService.create` (é um create genérico, sem side-effect); dar baixa na parcela e atualizar o status da fatura é responsabilidade do client aqui:
    1. `POST /v1/financial-transactions` (amount/payment_method/status escolhidos no mini-form, default `CONCLUDED`).
    2. Refaz `GET /v1/financial-transactions/by-installment/:id`, soma as `CONCLUDED`, compara com `installment.amount` (tolerância de 1 centavo — mesmo critério de `FinancialBillService.assertInstallmentsMatchTotal`, backend). Se bateu e `paid_out` ainda não estava `true`, `PUT /v1/financial-installments/:id` com `{ paid_out: true, paid_at: now }`.
    3. Recalcula localmente (a partir de `this.installments`, já carregado da fatura inteira): todas pagas → `PAID`; alguma paga → `PARTIALLY_PAID`; nenhuma → `OPEN`. Se `status` atual for `CANCELED`, não mexe. Se mudou, `PUT /v1/financial-bills/:id { status }` e emite `@Output() billStatusChange` pro `FormComponent` pai atualizar o controle `status` (usado na aba Dados Gerais).
    - **Trade-off aceito, mesmo padrão já usado no projeto (sync de endereços, self-register)**: essa cadeia de 2-3 requests não é atômica nem transacional — se o 2º/3º passo falhar depois do 1º ter sucedido, o pagamento fica registrado mas a parcela/fatura não refletem a baixa (recuperável reabrindo a fatura e registrando de novo, o cálculo é idempotente pela soma de transações `CONCLUDED`).
    - **`paid_by_id` (quem deu baixa) nunca é preenchido** — `AuthenticatedUser` (`@core/services/auth.service.ts`, decodificado do JWT) não carrega um `employee_id`, só `sub` (user id), `companies`, `roles`. Resolver o `Employee` do usuário logado exigiria um endpoint novo (`GET /v1/employees/by-user/:user_id` ou similar, não existe) — fora de escopo por ora.
  - **Resolução do `FinancialActor` (arco exclusivo devedor/credor)** — `FinancialActorService.getOrCreateForCustomer(customerId)`/`.getOrCreateForCompany(companyId)` (`@core/modules/financial/services/financial-actor.service.ts`): não existe endpoint REST dedicado tipo "by-customer" pro backend resolver isso, então a busca usa a própria query GraphQL genérica de listagem (`financialActorList`) filtrando por `customer_id`/`company_id` (`FilterParam`, mesmo mecanismo da seção 3.3), e cria via `POST /v1/financial-actors` se não achar nada. **Só chamado no `submit()` de criação** (edição não permite trocar devedor/paróquia, ver acima, então não precisa re-resolver o ator). A query GraphQL só pode pedir os campos que `FinancialActorEntity` expõe com `@Field()` no backend (`id`, `type`, `customer { id }`, `company { id }`) — **não dá pra selecionar as colunas escalares `customer_id`/`company_id` direto no corpo da query GraphQL** (só existem como coluna SQL, sem `@Field()`); usar `customer { id }`/`company { id }` e mapear na volta.
  - **`total` da fatura**: em criação, é sempre derivado da soma das parcelas em memória (campo `readonly`, recalculado via `valueChanges` do controle `installments`) — reflete a invariante do backend (`FinancialBillService.create` rejeita se a soma não bater). Em edição, vira um campo livre editável (o backend não recalcula `total` a partir de `items`/`installments` depois da criação — trade-off já documentado no `AI_CONTEXT.md` do backend §10 —, então aqui também não há sincronização automática pós-criação).
  - **Sem botão de excluir fatura na listagem** (diferente de Paroquianos/Funcionários/Serviços Financeiros) — decisão deliberada: `BaseCrudHttp.delete()` faz hard-delete (`DELETE /:id`, ver débito técnico §7), e uma fatura com parcelas que já têm transação bate no `RESTRICT` de `FinancialTransaction.installment` (backend), quebrando com erro de FK pouco amigável. Cancelar uma fatura é feito mudando `status` pra `CANCELED` na aba Dados Gerais (modo edição), não removendo o registro.

#### Armadilha de framework encontrada nesta tela: `@for` dentro de `ngbAccordionBody` quebra a change detection da página inteira

`NgbAccordionBody` (usado no `<div ngbAccordionBody>` dos filtros, seção 3.3 em diante) força um `ViewRef.detectChanges()` síncrono na primeira criação do body (`_createViewIfNotExists`), fora do ciclo normal de CD do Angular. Um `@for` (mesmo sobre um array plano montado uma única vez no `constructor`, não um pipe impuro tipo `keyvalue`) dentro desse body lança `TypeError: Cannot read properties of undefined (reading 'value')` (o `$implicit` do item chega `undefined` nesse check forçado) — e o erro **se repete a cada ciclo de CD daí em diante**, quebrando silenciosamente o resto da árvore de componentes daquela página: o sintoma mais concreto observado foi `@ViewChild` de componentes irmãos (`DataListComponent.modal`) nunca resolver, fazendo `new()`/`edit()` (que chamam `this.modal.show()`) lançar `Cannot read properties of undefined (reading 'show')` — o clique no botão "Novo Registro" simplesmente não abria o modal, sem nenhum erro visível na tela pro usuário. Nenhum filtro existente no projeto (`employees`, `parishioners`, `companies`, `addresses`) tinha `@for` dentro do accordion body antes desta tela — só usavam `<select>` com opções estáticas ou seletores async — então o bug nunca tinha aparecido. **Corrigido evitando `@for` (e por extensão o pipe `keyvalue`) para listas de opção fixas e pequenas dentro de `ngbAccordionBody`/abas do wizard**: os selects de `status`/`payment_method` (4-5 valores fixos cada, em `financial-bills/_components/filter`, `_components/form/basic` e `_components/form/installments`) viraram `<option>` estáticos, um por valor do enum, em vez de iterar. Se outro filtro/form precisar listar um enum pequeno e fixo dentro de um desses containers, replicar esse padrão (`<option>` estático) em vez de `@for`/`keyvalue` — só investigar `@for` de novo se a lista for dinâmica (não um enum fixo) e mesmo assim testar manualmente no navegador antes de dar por resolvido.

### 3.7 Cadastro de Usuário — tela SUPERADMIN-only, N vínculos (colaborador/paroquiano), perfis via checkbox (introduzido em `features/admin/users`, 2026-08-02)

Diferente das demais telas de CRUD (§3.3), `User` não tem (e propositalmente não ganhou) um `company_id` próprio — decisão explícita do usuário: a mesma pessoa pode ser colaborador de uma paróquia e paroquiano de outra ao mesmo tempo, então não existe "a empresa do usuário". Isso muda vários padrões em relação a Paroquianos/Funcionários:

- **Tela restrita a `RoleEnum.SUPERADMIN`** — dois endpoints novos e exclusivos pra essa tela, sem tocar nos que já existiam:
  - `POST /v1/users/admin` / `PUT /v1/users/:id/admin` (`UsersController`, backend) — únicos que aceitam `roleIds` (relação N:N `roles`, persistida via `repository.save()`, já que `BaseCrudService.update()` genérico faz `repository.update()` puro e não escreve relações). Guardados com `@Roles(RoleEnum.SUPERADMIN)` + `@UseGuards(AuthGuard, RolesGuard)` — o mesmo padrão de `company.controller.ts`, mas até então nunca aplicado em `users.controller.ts`.
  - **Por quê não estender o `POST`/`PUT /v1/users/:id` já existentes**: aqueles são usados hoje pelo self-signup público (`features/auth/sign-up`, sem `AuthGuard`) e pelo self-edit de perfil (`features/admin/user/user-profile`, `AuthGuard` mas sem checagem de role/dono — qualquer usuário autenticado pode chamar `PUT /v1/users/:id` pra **qualquer** `id`, não só o próprio). Aceitar `roleIds` ali deixaria qualquer usuário se auto-promover a `ADMIN`/`SUPERADMIN`. Os endpoints `/admin` resolvem isso separando completamente o caminho privilegiado do self-service.
- **Bug real corrigido de graça**: `UsersService.update()` (usado pelo `PUT` genérico, inclusive pela troca de senha em `user-profile/change-password.component.ts`) nunca hasheava a senha — `repository.update()` gravava texto puro por cima do hash bcrypt. Corrigido hasheando dentro do próprio `UsersService.update()` (override novo) antes de delegar pro `BaseCrudService.update()`. Beneficia tanto essa tela nova (aba Senha) quanto o self-service que já existia.
- **`UsersService.get()` ganhou `relations: ["roles", "roles.company"]`** — mesmo problema já mapeado em `CustomerService.get()`/`EmployeeService.get()` (§3.3): sem isso, a tela de edição carregava o usuário mas `roles` vinha sempre vazio.
- **Perfis (`Role`) não são mais escolhidos "dentro de uma paróquia selecionada"** — como um usuário pode ter perfis de várias paróquias, a aba "Perfis" mostra o catálogo inteiro (globais + de todas as companies), rotulado `Nome — Paróquia` ou `Nome (Global)`:
  - `RoleService` (front, novo, `@core/modules/acl/services/role.service.ts`) busca via GraphQL `roleList` existente (sem paginação real, `take` alto — catálogo tende a ser pequeno mesmo somando todas as paróquias).
  - **Não usa `Entity.toEntity()`** pra montar o resultado — mesmo motivo do `company-selector` (§7): o GraphQL não devolve `created_at` (backend serializa `createdAt`), então `toEntity()` geraria `Invalid Date`. ## 4. Comunicação com o backend

- O backend expõe **REST** (escrita) e **GraphQL** (somente leitura/listagem) — ver seção 2 do `AI_CONTEXT.md` do backend.
- Toda resposta REST vem envelopada no formato `Result` (`{ message, success, data, error }`). O service HTTP do frontend deve desembrulhar isso de forma **centralizada** (ex. um `HttpInterceptorFn` ou um wrapper único) — nenhuma tela deve acessar `.data` manualmente.
- Autenticação é Bearer JWT — o token deve ser anexado via interceptor central, nunca manualmente em cada request.
- A URL base da API fica no arquivo enviroment.ts dentro de src/environments de acordo com o ambiente adotado.
- O Cliente GraphQL usado para queries de listagem vai ser feito com Apollo Angular — **em uso pela primeira vez** na tela de Paroquianos (`customerList`, ver seção 3.3); antes disso o provider existia em `app.config.ts` mas com um endpoint placeholder nunca preenchido, então nunca tinha sido exercitado de verdade.

## 5. Formulários

- Reactive Forms tradicional ou Signal Forms (ainda experimental no Angular 21 — se optar por essa API, documentar aqui que é experimental e pode quebrar em upgrades de versão).
- Validação client-side deve espelhar as regras dos DTOs do backend (`create-*.dto.ts` / `update-*.dto.ts`), para o usuário não descobrir um erro de validação só depois do submit.
- **Validação cross-field (ex. confirmação de senha):** usar o `ValidatorFn` `passwordsMatchValidator()` em `@shared/validators/passwords-match.validator.ts`, aplicado no `FormGroup` pai (via `setValidators`) — ele seta o erro manualmente no `FormControl` filho de confirmação (`confirmPassword.setErrors({ passwordMismatch: true })`), pois cross-field validation não é expressável num Validator de controle único. Usado em `sign-up.ts` e `reset-password.ts` (`features/auth/`).

## 7. Débito técnico conhecido

- **`noImplicitReturns` desligado no `tsconfig.json`** (era `true`). O código do template (`sidebar.ts`, `search.ts`, `header-bookmark.ts`, `cart.service.ts`) usa `.filter()` como se fosse `.forEach()` — callbacks com efeito colateral e sem `return` em todos os caminhos — o que quebrava o build (`TS7030`). Em vez de reescrever esses componentes de terceiros, a flag foi afrouxada para todo o projeto. **A revisitar:** corrigir esses callbacks (trocar `.filter()` por `.forEach()`, cujo retorno era descartado) e reativar `noImplicitReturns`.
- **`CustomerService.selfRegister` (backend) não é transacional entre `User` e `Customer`** (ver [6.1](#61-auto-cadastro-público-vinculado-a-company-linkqr-code)) — são duas escritas em repositórios/módulos diferentes (`UsersService.create` depois `CustomerService.create`). Se a segunda falhar (ex. banco cai entre as duas chamadas), fica um `User` pendente órfão, sem `Customer`/company vinculados — caso raro, recuperável manualmente hoje. **A revisitar:** unificar numa transação real (`DataSource.transaction` cruzando os dois repositories) se o volume de auto-cadastro justificar.
- **`BaseCrudHttp.get(id)` (front, `@core/base/base-crud-http.ts`) tipado como `Observable<ResultModel<JsonProps>>`, mas usado como se devolvesse a `Entity` completa** — em `country-selector`/`state-selector`/`city-selector`/`address-selector`/`customer-selector`/`employee-selector`/`user-selector` (`autoset(id)`, seção 3.1), `result.data` é passado direto pra listas/eventos tipados como `Entity[]`/`EventEmitter<Entity>`, o que hoje quebra a checagem estrita de tipos do Angular (`ng test`/Karma falha ao compilar qualquer spec que importe esses seletores, com erro `Property 'toModel' is missing in type 'JsonProps'`), mas bloqueia testes automatizados de qualquer componente que dependa desses seletores — foi o caso do `address-form-list` (seção 3.2), cujo spec (`address-form-list.component.spec.ts`) está escrito mas não roda via `ng test` até esse tipo ser corrigido. Identificado em 2026-07-19, decisão explícita do usuário de não mexer agora (arquivos ainda em edição/não versionados). **A revisitar:** trocar o retorno de `get()` em `BaseCrudHttp` pra `Entity` (mesmo padrão que `create`/`update` deveriam seguir), então rodar `ng test` de novo.
  - **Correção em 2026-07-20**: a frase original desta entrada ("em runtime não quebra nada") **estava errada** — o campo `created_at` do JSON puro devolvido por `.get()`/`byLike()` é `undefined` (o backend serializa como `createdAt`, não `created_at` — ver bullet do bug de `Invalid Date` na seção 3.2), e o `Entity.toEntity()` chamado dentro do `autoset()` desses seletores gera um `created_at` do tipo `Invalid Date`. Isso só não quebrava nada **porque nenhum fluxo testado até então chamava `.toModel()` nesse resultado** — deixou de ser verdade assim que `address-form-list` passou a exigir país selecionado antes de liberar o resto do formulário (bloqueio bloqueia justamente pra garantir que o usuário passe pelo seletor). `CountryModel`/`StateModel`/`CityModel` já foram corrigidos; ver próxima entrada pros models que ainda não foram.
  - **`company-selector` não tinha o bug de `Invalid Date`, mas tinha esse mesmo erro de tipo — e nesse caso `ng build` quebrava de verdade, não só `ng test`.** Corrigido em 2026-07-20 ao finalizar a tela de Paroquianos (que usa `company-selector` no form e no filtro — foi o primeiro build real a exercitar esse componente e expor o erro). Diferente dos outros seis seletores, `CompanySelectorComponent.autoset()` foi corrigido **sem** usar `CompanyModel.Entity.toEntity()`: construindo a entidade direto (`new CompanyModel.Entity({ id, name })`), mesmo padrão que `CompanyService.byLike()`/`getPublicInfo()` já usavam nesse mesmo arquivo. Evita o erro de tipo e o bug de `Invalid Date` ao mesmo tempo (`new Entity()` sem `created_at` já cai no fallback certo do constructor). Se outro seletor da lista acima for exercitado por um `ng build` real antes de `BaseCrudHttp.get()` ser corrigido, essa é a forma mais rápida de resolver: construir a entidade só com os campos exibidos, não `toEntity()` do JSON cru completo.
  - **`customer-selector`/`employee-selector`/`address-selector` corrigidos em 2026-07-21** (`user-selector` já tinha sido corrigido antes) ao implementar os campos de núcleo familiar (pai/mãe) em Paroquianos: descoberto que esse erro de tipo **também quebra `ng build`/`ng serve` de verdade** (não só `ng test`), assim que qualquer tela real passa a montar >1 instância do mesmo componente de seleção na mesma página (o `customer-selector` reaproveitado para os campos "Pai"/"Mãe" do formulário forçou isso). Corrigidos com o mesmo padrão do `user-selector`: `Entity.toEntity(result.data)` dentro do `autoset()`, em vez de usar `result.data` (tipado como `JsonProps`) diretamente. Diferente do `company-selector` (que constrói a entidade na mão pra também evitar o bug de `Invalid Date`), aqui foi usado `toEntity()` mesmo — `AddressModel` já tinha o guard de `created_at` (seção anterior), mas `CustomerModel`/`EmployeeModel` **ainda não têm** (ver próxima entrada), então `customer-selector.autoset()`/`employee-selector.autoset()` seguem expostos ao bug de `Invalid Date` se algum fluxo futuro chamar `.toModel()` em cima da entidade emitida por `selected` (o formulário de Paroquianos não faz isso — só lê `.id` — então não quebrou desta vez).
- ~~**`Entity.toEntity()` ainda gera `created_at` como `Invalid Date` em `AddressModel`, `UserModel`, `RoleModel`, `CompanyModel`, `CustomerModel`, `EmployeeModel`**~~ **`AddressModel` corrigido em 2026-07-20** (mesmo guard `props.created_at ? new Date(...) : new Date()` já aplicado a `Country`/`State`/`City` — necessário porque `AddressesComponent.autoset()`, na tela de Paroquianos, chama `AddressModel.Entity.toEntity()` toda vez que a aba de Endereços é aberta, e qualquer edição subsequente de um endereço propaga esse `created_at` até um `.toModel()` real no submit). **`UserModel`, `RoleModel`, `CompanyModel`, `CustomerModel`, `EmployeeModel` continuam com o bug** (mesma causa raiz — o backend serializa `createdAt`, não `created_at`) — nenhum fluxo exercitado hoje força passar o resultado desses cinco por `.toModel()` depois de `.toEntity()`. **A revisitar:** aplicar o mesmo guard nesses cinco assim que algum fluxo novo precisar, ou — melhor — resolver a causa raiz (backend passar a serializar `created_at`/`updated_at`/`deleted_at` em vez de `createdAt`/`updatedAt`/`deletedAt`, ou o front normalizar isso num interceptor central).
- **`address-form-list` testado ponta a ponta em 2026-07-20, agora incluindo um navegador real** (Playwright headless via `chromium.launch`, contra `ng serve` local + backend em Docker): criação de paroquiano com paróquia + endereço (CEP real com autofill de rua/bairro/estado via ViaCEP), edição carregando o endereço já salvo, filtro por nome, remoção com confirmação. Ver seção 3.3 para os bugs específicos pegos só nesse teste em navegador (endpoint do Apollo, `FilterStore` fora do escopo de DI certo, `ngbNav` recriando aba + `@ViewChild` não resolvido em `ngOnInit`, `CustomerService.get()` sem relations, endereços não podendo ser aninhados no payload do customer) — **nenhum desses aparecia em `ng build`/`tsc`**, só ao clicar na tela de verdade; a entrada anterior (sessão 2026-07-19) validava só a cadeia de tipos fora do Angular via `tsx`, o que não seria suficiente para pegar esses bugs de runtime/DI.
- **Sincronização de endereços (`FormComponent.syncAddresses`, Paroquianos) não é atômica com a criação/atualização do customer** — mesmo trade-off já aceito em `CustomerService.selfRegister` (backend, seção 6.1): o customer é salvo primeiro, depois cada endereço é criado/atualizado/removido via requests HTTP separados (`forkJoin`). Se o customer salvar e algum endereço falhar no meio do `forkJoin`, fica um customer com endereços parcialmente sincronizados — recuperável reabrindo a edição e salvando de novo (o diff usa `originalAddressIds`, então tende a se autocorrigir na tentativa seguinte), mas sem rollback automático. **A revisitar:** se isso incomodar na prática, mover a sincronização pro backend (endpoint dedicado que recebe customer + endereços e roda tudo numa transação só) em vez de manter a orquestração no client — ver `AI_CONTEXT.md` do backend, seção 5.7.
- **`GET /v1/companies/by-like` (backend, novo endpoint pro `company-selector`) duplica lógica de filtro que já existe genericamente na query GraphQL `companyList`** (`BaseListArgs`/`BaseReportService.proccessFilter` já suportam filtro tipo `"like"` em qualquer campo, sem precisar de código novo por entidade). Foi implementado como endpoint REST dedicado — decisão tomada explicitamente com o usuário — pra manter `company.service.ts` (front) simples (uma chamada HTTP igual aos outros métodos do serviço, sem introduzir Apollo/GraphQL nesse ponto), mas isso diverge do padrão documentado na seção 4 (GraphQL = leitura/listagem, REST = escrita). Usa `Like` do TypeORM (não `ILike`, que é só Postgres — banco aqui é MySQL, já case-insensitive nas collations padrão). **A revisitar:** se surgir a necessidade de busca com autocomplete em outras entidades (funcionário, paroquiano etc.), decidir entre (a) generalizar esse `by-like` como endpoint reutilizável no `BaseCrudController`, ou (b) migrar pro padrão GraphQL genérico já existente, evitando reimplementar filtro por entidade.
- **Módulo financeiro (Faturas/Pagamentos, ver seção 3.6) — vários trade-offs client-orchestrated, mesma linha dos itens acima**: (1) registrar um pagamento e dar baixa na parcela/fatura são 2-3 requests HTTP separados, não uma transação — se um passo falhar no meio, fica um estado parcial recuperável reabrindo a fatura; (2) `paid_by_id` (quem deu baixa) nunca é preenchido, porque `AuthenticatedUser` não carrega o `employee_id` do usuário logado e não existe endpoint `by-user` pra resolver isso; (3) editar item de fatura já existente não é suportado (só adicionar/remover); (4) fatura não tem botão de remoção na listagem (só cancelamento via `status`), pra evitar bater no `RESTRICT` de `FinancialTransaction.installment` ao tentar apagar uma fatura com pagamentos já registrados. **A revisitar** se o volume de uso justificar: endpoint de "registrar pagamento" no backend que já faça a baixa em uma transação só, e/ou um jeito de resolver o employee do usuário logado.
- **Bug de framework `@for` dentro de `ngbAccordionBody` (ver seção 3.6)** — não é específico do módulo financeiro, é uma armadilha do Angular/`ng-bootstrap` que qualquer tela nova pode pisar de novo se introduzir um `@for` dentro de um filtro em accordion. Documentado ali com o sintoma (`@ViewChild` de componente irmão para de resolver, sem erro visível pro usuário) e a mitigação (usar `<option>` estático pra listas pequenas/fixas).
- **Cadastro de Usuário (ver seção 3.7) — sincronização de vínculos (colaborador/paroquiano) não é atômica**, mesmo trade-off de `syncAddresses` (Paroquianos)/módulo financeiro acima: o `User` é salvo primeiro, depois cada vínculo é uma chamada `EmployeeService.update`/`CustomerService.update` separada (`forkJoin`). Se uma falhar no meio, fica um estado parcial recuperável reabrindo a edição. **`RoleModel` continua com o bug de `Invalid Date` em `Entity.toEntity()`** (mesma causa raiz do item acima, nunca corrigido) — `RoleService` (novo) evita o problema construindo a entidade na mão (mesmo padrão do `company-selector`), então não foi exercitado por essa tela.
- **Mensagens de erro de negócio do backend não chegam ao usuário, em toda a API, não só em Batismos**: `BaseCrudController.httpException(msg, error)` sempre lança `HttpException(new Result(msg, false, null, error), 400)` com `msg` fixo em inglês (ex. `"It was not possible save register"`) — a mensagem real (ex. `"Este paroquiano já possui um registro de batismo"`, `BaptismService.create`, seção 3.8) vai dentro de `error`, mas como é um `Error` JS puro, serializa pra `{}` no JSON de resposta (propriedades de `Error` não são enumeráveis). Percebido ao testar a regra "um batismo por paroquiano" manualmente. **A revisitar:** backend passar a lançar `new HttpException(new Result(error?.message ?? msg, false, null, null), 400)` (ou similar) pra mensagens de negócio (`throw new Error(...)`) sobreviverem até o toast do front, em vez de sempre cair no genérico "Não foi possível cadastrar ou atualizar o registro".
- **Gap de multi-tenancy (`X-Company-Id`) sem solução no front — bloqueia teste manual de qualquer tela tenant-scoped com usuário vinculado a >1 paróquia** (ver `AI_CONTEXT.md` do backend, seção sobre `TenantContextInterceptor`): o front nunca implementou um seletor de "paróquia ativa" nem manda o header `X-Company-Id`, então um usuário com vínculo a mais de uma company (funcionário de uma + role em outra, por exemplo) recebe `400 User has access to multiple companies, header x-company-id is required` em **toda** query/list/by-like tenant-scoped, não só em Batismos. Descoberto testando Batismos manualmente (seção 3.8), contornado usando um usuário de teste vinculado a exatamente 1 company. **A revisitar:** implementar um seletor de company ativa no topbar (`@core/services/auth.service.ts` já decodifica `companies`/`roles` do JWT) que persista a escolha e a envie via um interceptor `HttpClient`/Apollo, igual o `authInterceptor` já faz com o Bearer token.
